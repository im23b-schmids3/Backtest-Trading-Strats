# ValueAreaTrap predeclared UTC variants

This is a fixed-variant exercise, not parameter research. It leaves the
completed `f1-ValueAreaTrap-aa3ec3068f16` baseline and all of its artifacts
unchanged.

The materializer creates three independent strategy IDs, versions, hashes,
planned run IDs, immutable parameter manifests, and an unexecuted comparison
template. It does not read the aggregate-trade Parquet, start a master run, run
a backtest, optimize a parameter, or create a Codex worktree.

```powershell
$manifest = '.\data\value_area_trap\normalized\BTCUSDT\908a22b85825a2c58cdf60d748500d403c16e57b52648a2376290547088f2b10\manifest.json'
python -m research_pipeline value-area-trap materialize-variants --data-manifest $manifest --artifact-root .\research_runs --repository-root .
```

The command only accepts that content-addressed dataset hash. Re-running it is
idempotent if every generated byte is identical; a changed existing manifest,
specification, parameter manifest, or comparison template fails closed.

The variants are:

| Variant | Strategy ID | Fixed difference |
| --- | --- | --- |
| `UTC_24H_SESSION` | `ValueAreaTrap.UTC_24H_SESSION` | UTC calendar-day session, right confirmation = 2, volume multiplier = 1.5 |
| `UTC_24H_FAST_SWING` | `ValueAreaTrap.UTC_24H_FAST_SWING` | Inherits A; right confirmation = 1 |
| `UTC_24H_FAST_SWING_VOLUME_125` | `ValueAreaTrap.UTC_24H_FAST_SWING_VOLUME_125` | Inherits B; volume multiplier = 1.25 |

Each UTC session is `[00:00:00, next midnight)` UTC. Therefore its final
included representable instant is `23:59:59.999999 UTC`. The current day uses
only the previous completed UTC day’s profile. The volume median is the ten
completed preceding 5-minute bars; the breakout bar cannot be in its own
reference median. A swing is emitted only after its configured right bars
close, and a trade is proposed no earlier than the following bar open.

After materialization, run one variant at a time with the exact `planned_run_id`
and paths emitted in the materializer JSON. For Variant A, for example:

```powershell
$root = '.\research_runs\ValueAreaTrap.UTC_24H_SESSION\f1-ValueAreaTrap.UTC_24H_SESSION-<HASH12>'
python -m research_pipeline --registry .\research_registry\research_pipeline.sqlite3 run "$root\run\variant-intake.json" --prebuilt-spec "$root\specification\specification.yaml" --run-id 'f1-ValueAreaTrap.UTC_24H_SESSION-<HASH12>' --mode real_run --data-manifest $manifest --allow-proxy-data --implementation-enabled
```

That normal F1/F2 command creates the usual approval boundary. It must not be
started for all variants together. Approve and resume each independently, using
the external Codex executor where the existing lifecycle requires it.

The resulting `value-area-trap-variant-comparison.json` begins as
`NOT_EXECUTED`. It reserves the fixed comparison fields required for each
variant: session/bar counts, stop-run and divergence counts, triggers, proposed
and executed/blocked trades, wins/losses, gross/net PnL, total costs, average
trade, profit factor, maximum drawdown, and Alpha MLL distance/breaches.

All artifacts and reports must retain the disclosure: **Binance BTCUSDT proxy
evidence; not CME or Alpha Futures performance.**
